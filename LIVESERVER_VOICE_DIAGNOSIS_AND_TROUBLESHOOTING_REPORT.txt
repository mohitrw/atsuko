2. THE 4 REASONS WHY THE BUG APPEARS EVEN ON LIVE SERVER
--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
CAUSE 1: WASAPI MICROPHONE DEVICE CONTENTION (THE DUAL-ENGINE CONFLICT)
--------------------------------------------------------------------------------
In the latest build, the voice system has two layers running:
  Layer 1: Offline DSP Keyword Spotter (AtsukoKWS in js/kwsEngine.js)
           Uses: navigator.mediaDevices.getUserMedia() via Web Audio API.
  Layer 2: Cloud Speech Recognition (SpeechRecognition in js/voiceAssistant.js)
           Uses: Chrome's native webkitSpeechRecognition to transcribe English words.

WHAT HAPPENS ON A FRESH MORNING LAUNCH ON WINDOWS:
1. When the page loads, Layer 1 (getUserMedia) grabs the Windows microphone
   device through Windows Audio Session API (WASAPI) with hardware constraints:
   { echoCancellation: true, noiseSuppression: true, autoGainControl: true }.
2. At the exact same time (350ms), Layer 2 (webkitSpeechRecognition) attempts
   to acquire the exact same microphone device to stream audio to Google's speech servers.
3. On Windows, when two independent browser subsystems attempt to hook into the
   same microphone hardware simultaneously:
     - The first stream (getUserMedia) locks the hardware capture pipe.
     - The second stream (SpeechRecognition) either fails with "audio-capture" error
       OR connects with a muted/silent audio feed (0 amplitude).
4. THE RESULT:
   - Layer 1 (KWS) or initial transcript hears "Night" and opens the assistant.
   - BUT Layer 2 (SpeechRecognition) cannot capture your voice for the command!
   - You speak the song name ("Play Blinding Lights"), but Chrome sends silence
     to Google servers.
   - The 6.5-second timer runs out, the assistant says "I didn't catch that",
     restores the volume, and closes!


--------------------------------------------------------------------------------
CAUSE 2: CHROME'S AUTOPLAY POLICY & "SUSPENDED" AudioContext STATE
--------------------------------------------------------------------------------
Chrome enforces a strict security policy called the "Autoplay / User Activation Policy":
  - When you were using the app last night, you had already clicked on buttons,
    songs, and sliders. The tab was "unlocked" (navigator.userActivation.hasBeenActive = true).
  - This morning, when you launched Live Server and opened a FRESH browser tab:
    The tab is initially "LOCKED".
  - In modern Chromium:
    new AudioContext() starts in state: "suspended"!
    Until you physically click anywhere on the webpage, Chrome REFUSES to allow
    the Web Audio engine to process incoming microphone samples.
  - If you say "Night" immediately upon opening the page before clicking anywhere:
    The AudioContext is suspended, so the processor node (onaudioprocess) is frozen.
    The microphone is literally sleeping until the first user click.


--------------------------------------------------------------------------------
CAUSE 3: THE SERVICE WORKER CACHE TRAP (sw.js "ignoreSearch: true")
--------------------------------------------------------------------------------
In your Service Worker (sw.js, Line 110):
  caches.match(e.request, { ignoreSearch: true })

Notice the setting: { ignoreSearch: true }!
Why this matters:
1. In index.html, we update script versions using query parameters:
   <script src="js/voiceAssistant.js?v=122"></script>
2. BUT because sw.js has "ignoreSearch: true", Chrome IGNORES the "?v=122"!
   It looks into the browser's disk cache for "js/voiceAssistant.js" without the query.
3. If Chrome has a stale version cached from two days ago (which had the syntax
   error or the 22-second idle killer interval):
   Chrome serves the STALE OLD SCRIPT to your page instead of the new code!
4. The Service Worker uses a "Cache-First / Stale-While-Revalidate" strategy:
   It serves the old broken script FIRST, and only downloads the new script in
   the background for the NEXT visit!
5. This is why it can work during testing, and then suddenly revert to an old
   broken behavior after restarting the browser.


--------------------------------------------------------------------------------
CAUSE 4: LIVE SERVER DYNAMIC PORT SHIFTING (http://127.0.0.1:5500 vs :5501)
--------------------------------------------------------------------------------
VS Code's "Live Server" extension has an automatic port-fallback behavior:
1. If port 5500 was left open by an orphaned background process overnight,
   VS Code silently launches Live Server on port 5501 (or 5502).
2. Look at the address bar in Chrome right now:
   Is it: http://127.0.0.1:5500/
   Or is it: http://127.0.0.1:5501/ (or 5502)?
3. WHY THIS BREAKS VOICE IN CHROME:
   In Chrome's security model, permissions are strictly bound to:
     [Protocol] + [Host] + [PORT]
   - If you granted microphone permission on port 5500 yesterday:
     chrome://settings/content/microphone -> http://127.0.0.1:5500 (ALLOWED).
   - If Live Server opened on port 5501 today:
     Chrome considers http://127.0.0.1:5501 to be a COMPLETELY NEW UNTRUSTED WEBSITE!
   - Chrome blocks the microphone until you click the address bar lock icon
     and explicitly allow microphone on port 5501.
