2. THE 5 CORE BROWSER SECURITY RESTRICTIONS ON "file:///"
--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
RESTRICTION 1: OPAQUE "null" ORIGIN VS. SECURE CONTEXT
--------------------------------------------------------------------------------
In web architecture, every webpage has an "Origin" consisting of:
  [Protocol] + [Domain / Host] + [Port]

- ON LIVE SERVER:
  Origin: "http://127.0.0.1:5500" or "http://localhost:5500"
  Chromium's W3C specification explicitly whitelists localhost and 127.0.0.1 as a
  "Potentially Trustworthy Origin" / "Secure Context" (window.isSecureContext === true).
  The browser grants full hardware access (Microphone, AudioContext, Web Speech).

- ON LOCAL FILE (file:///):
  Origin: "null" (an opaque origin with no hostname, no domain, and no port).
  In Chromium, window.isSecureContext evaluates as non-secure for cloud APIs.
  Chrome treats "file://" pages identically to sandboxed iframes.


--------------------------------------------------------------------------------
RESTRICTION 2: GOOGLE CHROME'S WEB SPEECH API ARCHITECTURE
--------------------------------------------------------------------------------
This is the single biggest technical factor:

Google Chrome's speech recognition engine (webkitSpeechRecognition) is NOT an
on-device software. Chrome records your voice and streams the raw audio chunks
over a secure WebSocket to Google's Cloud Speech Recognition servers
(https://www.google.com/speech-api/v2/recognize).

Google's cloud speech servers REQUIRE a valid HTTP/HTTPS origin header in the
handshake. When you open a local file directly:
  1. Chrome initiates webkitSpeechRecognition.
  2. The origin header sent is: Origin: null.
  3. Google's server rejects the connection, OR Chrome's security engine blocks
     sending microphone data over the network from a local file to protect user privacy.
  4. Chrome immediately fires: recognizer.onerror with error: "not-allowed" or "network".

On Live Server (http://127.0.0.1:5500), the origin is valid and accepted by
Google's speech servers without hesitation.


--------------------------------------------------------------------------------
RESTRICTION 3: CHROME PERMISSION PERSISTENCE (SITE SETTINGS)
--------------------------------------------------------------------------------
Why did you only have to grant permission once on Live Server, but on local files
it stops responding?

- ON LIVE SERVER & GITHUB PAGES:
  Chrome saves permissions in its internal SQLite database indexed by origin:
    chrome://settings/content/microphone
    Origin: "http://127.0.0.1:5500" -> State: ALLOWED (Permanent)
  Because permission is saved permanently, our background watchdog can restart the
  listener automatically every time a session resets without asking you again.

- ON LOCAL FILE (file:///):
  Because the origin is "null", Chrome CANNOT save the permission in Site Settings.
  There is no domain to attach the permission to!
  Once the first brief audio session ends (Chrome speech sessions naturally end
  every 20-30 seconds), Chrome refuses to let the script restart the microphone in
  the background because there is no persistent permission on disk.


--------------------------------------------------------------------------------
RESTRICTION 4: USER GESTURE REQUIREMENT FOR BACKGROUND AUTO-START
--------------------------------------------------------------------------------
In modern Chromium:
- On Secure Contexts (Live Server, GitHub Pages, PWA), a script can call:
    recognizer.start()
  automatically on page load (e.g., our 350ms startup delay) because permission
  is already saved in Site Settings.

- On "file:///", Chrome enforces strict "User Activation Gating":
  A webpage is strictly forbidden from accessing hardware (Microphone, Camera)
  unless the call is directly triggered by an active physical user gesture
  (e.g., clicking a button).
  When Atsuko loads via "file:///", the automatic background call at 350ms is
  blocked by Chrome's autoplay/hardware gating.
  If you click the microphone button manually, Chrome opens the prompt; but as soon
  as the first session closes, the background watchdog cannot restart it without
  another click.


--------------------------------------------------------------------------------
RESTRICTION 5: CORS (CROSS-ORIGIN RESOURCE SHARING) ON "file:///"
--------------------------------------------------------------------------------
When you double-click "index.html", Chrome isolates every local file for security:
  If JavaScript calls:
    fetch('./assets/atsuko-wake-sample.mp3')
  Chrome blocks it with the error:
    "Access to fetch from origin 'null' has been blocked by CORS policy:
     Cross origin requests are only supported for protocol schemes: http, https, data..."

This prevents the offline keyword spotter from reading local training audio files
when opened via "file:///", whereas Live Server serves them over standard HTTP 200 OK.
